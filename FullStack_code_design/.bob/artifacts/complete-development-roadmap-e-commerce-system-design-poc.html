Why Saga instead of 2PC (two-phase commit): 2PC locks DB rows across multiple services — a single slow service blocks everyone. Saga uses async Kafka events: each service does its work independently. If payment fails, a compensation event rolls back inventory. No distributed lock, no single point of failure.
💬 Interview answer: "We chose choreography-based Saga over orchestration because it keeps services fully decoupled — no central coordinator that becomes a bottleneck or single point of failure."

Why Idempotency is critical: Network timeouts happen. User clicks Pay → timeout → user clicks Pay again. Without idempotency key → charged twice. With it → second request detects key in Redis → returns cached success response → no second charge. Amazon, Stripe, Stripe all enforce this.
